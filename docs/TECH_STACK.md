### Products-within-category schema — `/architect` decision, 2026-09-26 (T-001)

Decided on the record, per T-001's acceptance criteria. Full DDL: `db/migrations/0001_products-within-category.sql` (same rationale repeated there as a header comment, for whoever applies it by hand).

**(a) Storage — new table for products; categories stay in JSONB, unchanged.** Categories (the 8 cards on `/what-we-do`: T-Shirts, Polo Shirts, etc.) continue to live exactly where they do today — `site_settings.business.products` (JSONB), edited by the existing `ObjectListEditor` in `BusinessClient.tsx` — with **zero changes to that editor's UI, fields, or save flow.** `VISION.md` is explicit that category CRUD already works and a design forcing that rebuild "needs a strong reason"; none exists, so no new table was created for categories, and none of their storage changed. Individual **products** (image/name/description, inside a category) get a **new table, `public.products`**, rather than a further-nested array inside each category's JSONB object. Reasons a table wins here: (1) VISION/T-003 describe per-product add/edit/delete/reorder as *single-item* operations, matching the `jobs`/`reports`/`leaders` per-row-CRUD pattern this codebase already uses three times for exactly this shape of problem — not the *whole-blob-Save* pattern the category editor uses. Nesting products under categories would force every single product edit to re-serialize and upsert the *entire* `business` JSONB value (all 8 categories' copy included) — unnecessary write amplification and a real lost-update risk the moment two admin edits overlap (a risk that's low-stakes today because category edits are rare, and would get worse, not better, if frequent per-product edits rode the same single whole-object Save). (2) A table gets a collision-proof primary key (`gen_random_uuid()` on insert) for free; JSONB would need application-managed IDs for the same guarantee. (3) `products` nested under each category would be the *first* doubly-nested array-of-array-of-objects shape ever stored in `SITE_SETTINGS`/`site_settings` — every existing array there is one level deep — and avoiding that novelty keeps `normalizeProducts`-style defensive parsing from growing a second nesting level of "what if this is missing" cases forever.

**(b) Attachment — an application-enforced `slug`, not a database foreign key.** Categories are JSONB array elements, not table rows, so Postgres cannot express a real foreign key from `products` to a "categories table" — there isn't one to reference. Each category object gains exactly one new field, **`slug`** (e.g. `"t-shirts"`) — computed once from its title, the first time it's saved without one, and frozen forever after. Renaming a category's title never changes its slug, so a rename can never orphan its products or change its public URL. `public.products.category_slug` stores that same value; the link is enforced entirely in application code (T-003's write path, contract below), never by the database. `slug` doubles as the public URL segment (`/what-we-do/<slug>`), so **T-005 needs no separate ID scheme.** Two categories can never resolve to the same URL because slug assignment is dedupe-checked at save time: a freshly computed slug that would collide with a sibling category's slug in the *same* save is **rejected outright** — the save fails with a specific, actionable error — never silently suffixed or overwritten. This matches, rather than invents a second style alongside, the "clear blocking message over silent auto-resolution" philosophy `VISION.md` already mandates for the delete-guard in (c). A *read-time-only* fallback (auto-suffixed, e.g. `-2`) computes a display slug for any legacy category that predates this field and hasn't been saved yet under the new code — to be added to `slugify()` / `normalizeProducts()` in `src/lib/site-content.ts` by `/lead-dev`'s types-only step (not yet present as of this decision; exact spec in the T-001 handoff) — but that fallback is never persisted by the read path, only by an actual save.

**(c) Delete guard — application check; a schema constraint is not possible.** Same root cause as (b): there is no category *row* for a `REFERENCES` / `ON DELETE RESTRICT` constraint to attach to — this is a structural fact of decision (a), not a discretionary choice. **Contract for T-003's `business`-settings write path:** before persisting a save, fetch the currently-stored category list; compute which category slugs are present in the old list but absent from the incoming one (a real delete — renames keep their slug, so a rename is never mistaken for one); run one grouped count — `SELECT category_slug, count(*) FROM products WHERE category_slug = ANY($removedSlugs) GROUP BY category_slug` — against exactly those removed slugs; refuse the *entire* save with a specific, named-category error (e.g. "Remove its products first") if any of them is non-zero. The composite index created in `0001` (`products (category_slug, sort_order)`) serves this count query as well as the ordered product listing, via its leftmost column — no second index needed.

**No new package.** Slug generation was evaluated against an npm `slugify`-style package and refused: it's a ~10-line pure function (lowercase, collapse non-alphanumerics to hyphens, trim) with no edge case this project needs that justifies a dependency — fails "does it earn its keep," independent of whether something 80%-there already exists.

**Follow-up, same day — explicit GRANTs added to `0001`.** `/system-architect` correctly flagged that RLS policies only filter rows a role already has table-level privileges for; GRANT is checked first, RLS second, and this project's `supabase-schema.sql` has zero explicit GRANT statements for any of its six existing tables (they work today purely on Supabase's project-level default privileges, which historically auto-grant SELECT/INSERT/UPDATE/DELETE to `anon`/`authenticated`/`service_role` on every new `public` table). That default is being phased out platform-wide: an opt-out toggle ("automatically expose new tables") has existed since 2026-04-28, becomes the default for brand-new projects from 2026-05-30, and is **enforced on existing projects — this one included — from 2026-10-30**, roughly five weeks from this decision. `0001` sits as `PENDING_USER_APPLY` with no fixed apply date, and the project's own toggle state can't be verified from here regardless of that deadline. Added `GRANT SELECT ON TABLE public.products TO anon;` and `GRANT SELECT, INSERT, UPDATE, DELETE ON TABLE public.products TO authenticated;` — matching Supabase's own documented recommendation verbatim, scoped to exactly what the two RLS policies already intend, no `service_role` grant (this project has no service-role key anywhere in `src/`). `GRANT` is natively idempotent in Postgres (unlike `CREATE POLICY`), so no guard block was needed. Reassurance for the other five tables: `ALTER DEFAULT PRIVILEGES` is create-time-only, so the 2026-10-30 enforcement does not retroactively strip grants already made when those tables were created — only *new* tables (i.e. `products`) are at risk. **Not actioned, flagged only:** backporting explicit grants onto the other five tables as defensive hardening (they're not at risk, but stating their access outright rather than relying on an inferred, soon-to-be-atypical default would be more legible) — a candidate for its own low-priority follow-up ticket, not bundled into `0001`.

### Category identity amendment — /architect decision, 2026-09-27 (T-003: closes QA CRIT-1 + CSO SEC-HIGH-3)

**Trigger.** `/qa static T-003` failed with 🔴 CRIT-1 (`docs/QA_REPORT.md`) and `/cso`'s T-003 review carries an open 🟠 SEC-HIGH-3 (`docs/SECURITY.md`). Both trace to one root cause in `resolveCategoriesForSave`/`updateSettings`: a category's slug is trusted forward, and a deletion is detected, by **bare slug-string membership** in a set, with no record of *which category row* actually owns a given slug. Closed here, for both findings at once, by giving categories a second, purely internal identity field. No code is written by this entry — this is the decision record; the implementable spec goes to `/lead-dev` directly.

**(d) Category identity — a server-issued `id`, carried in the same JSONB element as `slug`. No new table, no migration.** Every category object gains a second field, **`id`** — a server-generated `crypto.randomUUID()` string (Node builtin; same primitive `gen_random_uuid()` already mirrors at the Postgres layer for `public.products.id`, T-001 — precedent, not a new pattern), assigned the first time a category is saved without one, frozen forever after, exactly mirroring `slug`'s own lifecycle from decision (b). Unlike `slug`, `id` is **never a public value**: not a URL segment, not rendered in `/admin` or on the public site, not one of `ObjectListEditor`'s editable fields, not written to or read from `public.products` (attachment there is still, and remains, by `category_slug` alone — decision (b)/(c) unchanged). This needs **no DDL**: `site_settings.business.products` is JSONB, and `id` is one more key inside each array element, added exactly the way `slug` itself was added at T-001 with zero migration. No other design here was found to need a schema change, and none is proposed.

**Why an `id`, not a stricter slug rule.** A tempting alternative — "a freshly-derived slug may never reuse any currently-stored slug, even one being removed in the same save" — was considered and rejected: it closes CRIT-1 but not SEC-HIGH-3 (SEC-HIGH-3 is a *carried*-slug hijack, not a *freshly-derived*-slug collision; a stricter fresh-slug rule has nothing to say about it), and it would regress a harmless, common action — delete an empty category and immediately re-add one under the same name in one save — with no safety benefit. `id`-based provenance closes both findings as one mechanism, not two patches, and still permits that harmless case (see "Fresh-slug reuse," below).

**When a stored slug may be carried forward — matching is by `id` alone, never by slug, never by title.** On every `business` save, `updateSettings` re-fetches the currently-persisted row (unchanged practice) and builds a map keyed by each existing category's own `id`, of `{slug, title}` (`existingById`). Per incoming item: if it carries a non-empty `id` found in `existingById`, it is the **same category** regardless of title/description/image/array-position changes — its slug is **looked up by that `id`** and reattached verbatim; **the incoming item's own `.slug` field is never read for this decision.** A rename changes nothing about slug/id. Otherwise (no `id`, or an `id` absent from `existingById`) it is a **new** category: fresh `id` (`randomUUID()`), fresh slug (`slugify(title).slice(0, 255)`, unchanged from (b)) — again, **the incoming item's own `.slug` field is never read.** Net effect: a client can no longer propose a slug value under any circumstance, ever — every stored slug is either looked-up-by-id or `slugify()`-derived. Two incoming items claiming the same existing `id` reject the whole save by name before either is resolved further. This also resolves the ambiguity `/cso`'s own SEC-HIGH-3 mitigation note flagged — distinguishing a genuine rename from a slug donated to a different row — by never inferring anything from title at all.

**The collision rule is unchanged in mechanism, now correctly scoped.** Every resolved item's slug (looked-up or fresh) is still checked against every slug resolved earlier in the same save, in array order — the existing `seenSlugs` logic, decision (b). The first collision anywhere still rejects the **whole save** with a specific, named-category error, order-independent. What changes is that a slug can no longer be silently reassigned to the wrong row *before* this check runs, because ownership is no longer inferred from the string itself.

**Fresh-slug reuse of a slug vacated in the same save — allowed, gated by the delete-guard's own product check, never silent.** A new category's freshly-derived slug *may* equal a slug an existing category is losing in the same save. This is deliberately not blocked by a blanket rule, because the delete-guard (below) already blocks the unsafe version more precisely: if the vacated category still has ≥1 product, the whole save is rejected regardless of what any other item claims or resolves to, before "who gets the freed slug" is even reachable. If the vacated category has zero products, reuse is genuinely harmless. Direct answer to "does a fresh slug ever get to reuse a slug removed in the same save": **yes, conditioned on the delete-guard's product count for that specific category — never unconditionally, and the guard's rejection, when it fires, still names the category and still fails the whole save.**

**How `removedSlugs` / the delete guard is computed — by `id`-diffing, never by slug-string-diffing.** This is the line CRIT-1 and SEC-HIGH-3 both actually broke. A category is genuinely removed when its `id` (present in the fresh `existingById` pre-fetch) does **not** appear among the `id`s of `resolveCategoriesForSave`'s resolved output. Its slug — looked up from that same `existingById` map, never re-derived, never taken from the incoming payload — is what the guard's product-count query checks. A brand-new item that happens to compute the identical slug string (CRIT-1) can no longer make a real removal invisible, and a carried-forward item claiming the vacated slug as its own (SEC-HIGH-3) can no longer make a real removal invisible either — in both cases the *row* is genuinely gone from the resolved output, so its slug is correctly flagged and checked against `public.products`, independent of what any other item in the same save resolves to.

**Malformed stored slugs — re-validated at the moment they'd be carried forward; rejection is whole-save.** A stored slug can only be malformed today via manual DB editing (this write path only ever assigns `slugify()`-clean values, and zero live categories carry any stored slug or `id` as of T-001's Live Pass) — but "frozen forever" was always meant to apply to a *validly*-assigned slug. When an incoming item's `id` resolves via `existingById`, that row's recorded slug is checked against the shape `slugify()` is provably confined to (SEC-INFO-12) before reuse; a slug that fails rejects the **whole save**, naming the category, rather than silently persisting an invalid value forward again. A malformed slug on a row being genuinely *deleted* in the same save is not re-validated for shape — there is nothing to carry forward — it is simply checked as-is against `public.products.category_slug` by the unchanged, parameterized delete-guard query, which is safe regardless of its shape.

**Missing or non-array `products` payload — rejected outright, not coerced to zero categories.** The prior behavior (`!Array.isArray(raw)` → `{ok:true, categories:[]}`, covering `raw === undefined` too) is replaced with an explicit `{ok:false, error:"..."}`. Unreachable through the shipped UI (`BusinessClient.tsx` always sends its full array-typed state) — the fix is for any direct or malformed call, per `/cso`'s SEC-MED-6, which correctly named the old behavior's worst case: every currently-stored category treated as "removed," gated only by whether each happened to have zero products that day.

**Client dependency — what T-004 must preserve, and what it cannot break.** No change to `SettingsForm.tsx`/`ObjectListEditor` or `BusinessClient.tsx` is required by this fix: `id`, like `slug`, is not one of `ObjectListEditor`'s editable `fields`, so its existing spread-based `update()`/whole-object `move()` already round-trip an unknown extra key correctly, and `blank()`'s new-row shape (no `id` key at all) is exactly what the "new category" branch expects. **Every safety/data-integrity guarantee here holds regardless of T-004's implementation** — the server never trusts the client for identity, only for content. What does depend on T-004: if its rebuild reconstructs category objects from scratch instead of preserving unknown keys, every save looks like "all categories are new" — no data is lost or exposed (a fresh `id`+slug is simply minted every time; the delete-guard and collision-check both still hold), but a rename's slug stops staying frozen, regressing decision (b)'s URL-stability half to first-save behavior on every edit. Flagging as an explicit T-004 acceptance-criterion candidate — round-trip `id` (and `slug`) for any category the admin didn't explicitly delete — for `/pm` to fold in; not re-litigated here.

**No package.** Same "does it earn its keep" refusal already on record for `slugify()` at T-001 applies identically to `id` generation — `crypto.randomUUID()` is a one-line Node builtin.

**Follow-up, same day — legacy (id-less) categories must be bootstrapped by a save before products may attach; closes a residual CRIT-1-shaped gap in `products-actions.ts`.** `/system-architect` correctly flagged what decision (d) above missed: `getValidCategorySlugs()` (`src/app/actions/products-actions.ts`) validated a product's `category_slug` against `normalizeProducts()`'s read-time, ephemeral, auto-generated slug — the fallback that exists purely so a page always has *something* to render for a category that predates this feature. That fallback was never meant to make a category *attachable*, only *displayable*. Today's 8 live categories have no stored `id` (T-001 Live Pass) — so once T-004 ships, staff could attach real products to, say, "T-Shirts" using its ephemeral `t-shirts` slug before that category has ever been through a real `/admin/business` save. If that category's first real save also renames it, `existingById`/`readStoredCategoryIdentities` (below) has no entry for it — the row correctly resolves as brand-new per decision (d) — but `computeRemovedCategories` then has nothing to report, because there was never a frozen `id` to lose, and the products already sitting under the old slug silently orphan. Same failure class as CRIT-1, reached through a different door, and reachable by a plain rename alone — no delete-and-re-add needed.

Two alternatives were considered and rejected, not just deprioritized: **(1) extending the delete-guard to diff id-less rows' *computed* slugs against the resolved output** is unsound — replaying CRIT-1's own maneuver against an id-less row reproduces the identical bug, because a fresh row's coincidentally-matching computed slug still satisfies "this slug string is still present somewhere," for precisely the rows most likely to hold real data today. There is no sound way to distinguish "renamed" from "replaced" without a persistent identity — that ambiguity is the entire reason `id` exists, and no slug-level patch removes it. **(2) Having `createCategoryProduct` silently auto-mint ids/slugs for the whole category row on first attach** is sound (the bootstrap write only ever re-persists the row's own unmodified content, so it cannot move any observable slug) but was rejected as disproportionate: it introduces a hidden, cross-cutting write triggered by an unrelated action — no other write path in this codebase does that — for a threat model (`docs/SECURITY.md` SEC-MED-5: "a small, hand-created admin roster, not concurrent public traffic") that doesn't need it. Worth reconsidering only if T-004's UX later makes the manual step genuinely painful.

**Ruling: products may only attach to a category that already has a genuine, stored, well-formed `id` + `slug` — i.e., has survived at least one save under decision (d).** `getValidCategorySlugs()` is removed from `products-actions.ts`. Every write there (`createCategoryProduct`, `updateCategoryProduct`, `reorderCategoryProducts`) instead checks the target `category_slug` against only the **frozen** identities, read via a new shared helper — `readStoredCategoryIdentities()`, factored out of `updateSettings`'s own pre-fetch parsing and exported from `site-content.ts` for both files to share — never against `normalizeProducts()`'s display fallback. A category that exists but hasn't been saved yet under the new scheme is a distinct, named error case (`"not_yet_bootstrapped"`, carrying the category's own title), never lumped in with "does not exist" — the fix is always the same one-time action: open `/admin/business` and click Save once, no other change required, which mints `id`+`slug` for every category in the row at once, including ones nobody touched. **Operational note, not a migration:** `public.products` is empty today — T-003 and T-004 have never shipped — so this closes before any live data is at risk. Flagging for `/pm`/T-004: the one-time bootstrap-save requirement should be a named T-004 acceptance-criterion bullet and a line in whatever manual checklist accompanies T-004's `/qa live` pass.

## Notes for implementers

- **Naming quirk, T-001 (2026-09-26).** `site_settings.business.products` (the JSONB key) and the TypeScript `Product` type in `src/lib/site-content.ts` both hold **categories** (T-Shirts, Polo Shirts, ...), not the new individual catalog items — the name predates this feature and was deliberately left unchanged, to avoid touching `BusinessClient.tsx` / `business/page.tsx` / `what-we-do/page.tsx` (all outside T-001's file list) and to avoid a live-data key rename. The new per-category catalog items — VISION.md's actual "product": image/name/description — are the **`CategoryProduct`** TypeScript type and the new **`products`** SQL table. Do not conflate the two "products." `Product.slug` (T-001's schema decision, (b) above) is a category's permanent identity and public URL segment, and is **live in code today**: `slugify()`, `dedupeSlug()`, and the read-time carry-forward/fallback logic all sit in `src/lib/site-content.ts::normalizeProducts()`; the save-time write path (collision-checked, then id-scoped per decision (d)) is `resolveCategoriesForSave()`/`updateSettings()`, which T-003 implemented — see the Database section above for the full contract. *(Corrected 2026-09-27 — this bullet previously called `Product.slug` "not yet in code," true only before T-001 shipped it; flagged stale in `docs/MEMORY_BANK.md`'s T-001 entry and left uncorrected through T-003.)*
- **Amendment, 2026-09-27 (T-003 — Category identity).** `Product` (category) now also carries `Product.id` — a category's own internal identity, server-issued, never public, never displayed, never one of `ObjectListEditor`'s editable fields, never written to or read from `public.products`. Do not confuse this with `CategoryProduct.id`, the real DB-generated UUID primary key of an individual product **row** in `public.products`, used throughout `products-actions.ts`. Two different types, two different `id` fields, two different purposes: `Product.id` lets a `business` save tell "the same category, edited" apart from "a different category" (`resolveCategoriesForSave`/`updateSettings` in `settings-actions.ts`) — and that same stored value is also what `products-actions.ts`'s `checkCategoryAttachable()` reads, via the shared `readStoredCategoryIdentities()` helper exported from `site-content.ts`, to decide whether a category has been bootstrapped and may accept products (Database section above, the same-day "legacy (id-less) categories" follow-up). `CategoryProduct.id` remains the separate thing every read/write in `products-actions.ts` keys on for product rows themselves. *(Corrected 2026-09-27 — this bullet previously said `Product.id` is "never read outside `resolveCategoriesForSave`/`updateSettings`"; true only until the same-day bootstrap follow-up extended `readStoredCategoryIdentities()` into `products-actions.ts` too.)*
- **Server Action failure-reporting convention (2026-09-27; prerequisite for SEC-HIGH-4, `docs/SECURITY.md`, due with T-004).** `products-actions.ts` (T-003) already returns a typed result from every write action — `{ ok: true, ... } | { ok: false, error: string }` — for its caller to branch on. `settings-actions.ts`'s `updateSettings` still `throw`s a plain `Error` for the equivalent class of user-facing guard failure (auth, slug/id collision, delete-guard, malformed payload); Next.js redacts a thrown Server Action message to a generic string in production, and none of the 7 settings-page admin clients catch it today. Convention going forward: **a user-facing guard failure is returned as a typed `{ ok: false, error }` result, never thrown; `throw` is reserved for genuinely unexpected/infrastructure failures** (a DB connection error, a bug), where falling through to a generic error boundary is the correct behavior. Every caller of a Server Action that can return `{ ok: false }` must handle that branch — awaiting the call and ignoring the result is a bug. This entry does not itself convert `updateSettings` — that conversion is SEC-HIGH-4's fix, owned by whichever ticket picks it up — it only fixes the pattern so T-004 and later admin work don't each invent a different shape.
