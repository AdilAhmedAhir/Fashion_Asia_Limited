### Findings

- 🟡 **WARN-1** — `checkImageSizeAdvisory` silently mis-reports `offProportion` for a 0×0 image — `src/lib/upload-limits.ts:98-99` — `ratio = width / height` is `0/0 = NaN` when both are zero; `NaN < 1` and `NaN > 2` are both `false` in JS, so `offProportion` comes back `false` instead of `true`, while `tooSmall` correctly comes back `true`. Net effect: a warning still fires (not a silent-failure bug), but it always claims "smaller than the recommended…" and never "a noticeably different shape," which is a strange thing to say about a 0×0 image. Trigger condition is narrow: `img.onload` firing with `naturalWidth === naturalHeight === 0` for a genuinely-decoded JPEG/WebP is close to unreachable (both formats always encode non-zero dimensions in their header on a successful decode; an actual decode failure fires `onerror`, not `onload`, and is already handled at `ImageUploadField.tsx:108-111`). The realistic path in, if any, is a mislabeled non-raster file (e.g. a sizeless SVG renamed to `.jpg`) that some browser decides to decode anyway — client-side format sniffing hasn't run yet at this point (`sniffImageFormat` is server-side only, later). No crash, no hard-block bypass, no data corruption — purely a cosmetic mis-statement inside a non-blocking advisory string. **Fix proposal:** guard the division, e.g. `const ratio = height === 0 ? Infinity : width / height;`, or short-circuit to `{ tooSmall: true, offProportion: true }` whenever `width <= 0 || height <= 0`.

- 🟡 **WARN-2** — Rapid successive file picks race; whichever upload's network round-trip resolves *last* wins, not whichever was picked last — `src/components/admin/ImageUploadField.tsx:97-139`. `handleFile` is re-entrant with no guard: the file `<input>` (`:209-219`) and the drop zone are never `disabled`/inert while `busy` is `true`, and there is no request-sequence token, no `AbortController`, no "ignore a stale resolution" check. If a staff member picks file A, then — before A's `readDimensions` + `uploadOptimizedImage` round trip finishes — picks file B, both invocations run concurrently. Each clears `error`/`warning` via its own `setError(null)`/`setWarning(null)` at entry (so no simultaneous stale display), but the *last* promise to resolve calls `onChange(result.url)` + `setWarning(advisory)` last, overwriting whatever the other call already wrote — even if that means the field ends up showing file A's image/warning when the user's actual last action was picking file B. **Pre-dates T-002** (the old `tooBig` was awaited the same unguarded way) — T-002 doesn't introduce the race, but it does add a second piece of state (`warning`) that now rides the same unguarded race the image `value` already had. Impact is a confusing-but-recoverable admin-UI moment (re-picking fixes it; both files still separately land in storage — only the client's *displayed* final state can pick the "wrong" one), not a security or data-integrity issue. **Fix proposal:** disable the input/dropzone while `busy`, and/or track a monotonic "latest pick" ref and ignore a resolution that isn't from the latest call. Recommend a `/pm` follow-up rather than reopening T-002 for pre-existing behavior it didn't originate.

- 🟡 **WARN-3** — Manually editing the raw path `<input>` (`ImageUploadField.tsx:248-255`) doesn't clear a stale `warning`/`error` left over from a previous upload attempt on the same field instance — the reset at `:98-99` only runs inside `handleFile`, which the path `<input>`'s own `onChange={e => onChange(e.target.value)}` never calls. Repro: upload a small photo (warning appears: "smaller than the recommended…"), then use the same field's editable path box — kept editable on purpose, "the built-in photographs are repo paths, not uploads" (`:247`) — to switch to a different, already-correctly-sized built-in image path. The thumbnail and stored `value` correctly update, but the old warning stays on screen describing an image that is no longer selected. The same gap already existed for `error` before T-002; this diff adds a second instance of it. Cosmetic/misleading, not a data bug — the saved `value` itself is always correct. **Fix proposal:** also clear `error`/`warning` inside the path `<input>`'s `onChange` handler.

- 🟡 **WARN-4** — Reordering or deleting a product/facility-photo row can hand one item's leftover warning/error to a *different* item's upload field — root cause is **outside T-002's diff**, in `src/components/admin/SettingsForm.tsx:167` (`{items.map((item, i) => (<div key={i} …>`) and `:192-193` (`<ImageUploadField key={f.key} … value={item[f.key] …} />`). The outer per-row key is the array index `i`, not a stable per-item id, so React reconciles a reordered/shortened list by re-rendering the *same* `ImageUploadField` instances at each index with new `value` props rather than mounting fresh ones — the field's own local `error`/`warning`/`busy` state (only ever reset inside `handleFile`, see WARN-3) survives the reorder attached to whatever now occupies that slot. Concretely: product #1 gets a "smaller than recommended" warning; staff clicks "move down" on product #2 (swapping #1 and #2); product #2's image field — now at array index 0 — inherits and displays product #1's stale warning, describing product #1's dimensions, not its own. Same mechanism on delete for every row after the deleted one. Reachable today from `/admin/business`'s "Product Cards" `ObjectListEditor` (move-up/move-down/remove buttons render unconditionally) and from `/admin/homepage`'s facility-photo list. **Not a T-002 regression** — `SettingsForm.tsx` isn't in this ticket's file list and this diff doesn't touch it — but T-002 makes the *consequence* more visible, since "too small"/"off-proportion" warnings will fire far more often in practice than the rare hard-block error the same gap already affected. Consistent with `docs/ROADMAP.md` T-001's own acceptance criteria, which already flags that `site_settings.business.products` items have no stable id yet (`src/lib/site-content.ts:318-322` — `Product` is `{ title, description, image }`, no `id`) — a real per-item key isn't available until T-001 lands. **Fix proposal:** once T-001 provides a stable id, key `ObjectListEditor`'s rows by that id instead of index; until then, at minimum have `ImageUploadField` reset `error`/`warning` whenever its `value` prop changes for a reason other than its own `handleFile` call. Recommend a `/pm` follow-up ticket; does not block T-002.

- 🟢 **INFO-1** — Wording nit at extreme aspect ratios — `src/lib/upload-limits.ts:97` — `tooSmall` is `width < 1200 || height < 900`, an OR across two independent dimensions, so a very wide/short image that still clears the 2400px hard cap (e.g. 2400×100) is labeled "smaller than the recommended 1200×900px" even though its width is exactly 2× the recommendation — only its height is short. The shown numbers (`This image is 2400×100px…`) are still accurate, so nothing is factually wrong, just slightly imprecise about which dimension is the actual problem. Not worth blocking on.

**4. The order-dependence question the dispatch asked directly: "stored `t-shirts` on item 2 vs. computed `t-shirts` on item 1 — does order change the outcome, and is it stable across reads?"** Answer: **yes, order changes the outcome, and it is only stable across reads of a fixed, already-written array — not across a save that reorders or adds a colliding title.** Reproduced directly:

```
Order A — computed-slug item FIRST, stored-slug item SECOND:
[ { title: 'T Shirts',  slug: 't-shirts' },     // computed fresh, seen was empty → no collision detected
  { title: 'T-Shirts',  slug: 't-shirts' } ]     // storedSlug taken verbatim, never checked against `seen`
  → BOTH items end up with the identical slug "t-shirts". Silent. No error. No log.

Order B — same two items, reversed:
[ { title: 'T-Shirts',  slug: 't-shirts' },      // storedSlug taken verbatim, added to `seen` first
  { title: 'T Shirts',  slug: 't-shirts-2' } ]   // computed, seen already has "t-shirts" → correctly caught
```

This is the exact mechanism the dispatch asked me to hunt for, confirmed by execution, not inference.

### Findings

- 🟡 **WARN-1 — `normalizeProducts()`'s stored-slug bypass is order-dependent, and reachable through ordinary `/admin/business` use, not only through manual dashboard/SQL editing as `docs/SECURITY.md`'s SEC-MED-3 characterizes it.** `src/lib/site-content.ts:406-408` — `const slug = storedSlug || dedupeSlug(slugify(title), seen);` — whenever `storedSlug` is truthy, `dedupeSlug` is skipped entirely: the stored value is used as-is and only *added to* `seen` afterward, never *checked against* it first. SEC-MED-3 correctly identifies this line and its stored-vs-stored failure mode, but frames live-reachability as "possible today only via manual dashboard/SQL editing, since no shipped write path sets this field yet." I verified a **stored-vs-computed** variant of the same bug (demonstrated above, Order A) that is order-dependent: if a category *without* a stored slug is processed before a sibling *with* a colliding stored slug — which happens the instant array order places the unsaved item first, e.g. after using `ObjectListEditor`'s own "move up" button (`SettingsForm.tsx:152-158`, a plain array-position swap with no re-validation) — the collision is **not** caught at all, by either category, and both silently resolve to the same slug. This needs no dashboard/SQL access: adding a category with a title that slugifies to an existing sibling's stored slug (a plausible copy-paste/typo scenario — e.g. "T Shirts" vs. the real "T-Shirts") and then moving it above that sibling is entirely achievable through the existing, unmodified `/admin/business` UI. Not exploitable *today* in the sense that zero categories in the live database carry a stored `slug` yet (confirmed: T-001's migration never touches `site_settings`), but the trigger condition is materially broader than "manual DB editing," and directly relevant to WARN-2 below. **Also verified:** computed-vs-computed collisions (no stored slug on either side) are correctly caught regardless of order, because both go through `dedupeSlug` unconditionally — the bug is specifically and only in the stored-value bypass. **Fix note:** CSO's proposed one-liner (route the stored branch through `dedupeSlug(storedSlug, seen)` too) would trade this failure mode for a different one — it would let a sibling's processing order silently *change* an already-established category's permanent slug/URL, which is exactly what decision (b) promises never happens ("frozen forever after"). Neither "let the collision through" (today's behavior) nor "silently reassign the stored slug" (the naïve fix) matches the ticket's own "no silent resolution, ever" principle — the only fix that actually matches the decision record is detecting the collision and refusing to resolve it silently in *either* direction, which is inherently a save-time (T-003), not read-time, guarantee. **Recommend:** fold into T-003's acceptance criteria as a named, testable bullet (not just "recommend folding in" — make it explicit that T-003 must handle categories that already carry a stored slug colliding with another category's title-computed slug, which — per WARN-2 — can arise before T-003 ships).

- 🟡 **WARN-2 — the "reject the entire save on collision" guarantee decision (b) promises does not exist in any shipped code yet, and — this is the new finding, distinct from anything in `docs/SECURITY.md` — the pre-existing, unmodified `/admin/business` Save button already silently *persists* whatever `normalizeProducts()` computed at page load, the moment any admin clicks Save for any reason, well before T-003 exists.** Traced the full read → state → save round trip: `business/page.tsx:8` calls `normalizeProducts(data.products)` on load, which now attaches a `slug` to every category object in memory (computed fresh if none was stored). `BusinessClient.tsx:17` puts that array straight into `useState`. `ObjectListEditor`'s `update()` (`SettingsForm.tsx:146-150`) does `next[index] = { ...next[index], [key]: val }` — it spreads the *entire* existing item (including the in-memory `slug` `normalizeProducts` attached) and only overwrites whichever field the admin actually touched (`title`/`description`/`image` — `slug` is not in `ObjectListEditor`'s `fields` list and is never shown, confirmed). Clicking "Save Changes" (`BusinessClient.tsx:22-24`) sends the *entire* `data` object, `slug` included, straight to `updateSettings("business", data)`, which (`settings-actions.ts:39-43`) does a raw `upsert({key, value, ...})` with **no field allow-list, no transform** — whatever is in the client's React state is written to `site_settings.business` verbatim. Net effect: the very first time any admin edits *anything* on `/admin/business` (a routine description typo fix, nothing to do with slugs) and clicks Save, every category's computed slug — including one already silently colliding per WARN-1 — gets **permanently frozen into storage**, with zero error, zero log, zero admin-visible signal, directly contradicting the migration file's own header prose ("a freshly computed slug that would collide… is REJECTED outright… not silently suffixed, not silently overwritten," `db/migrations/0001_products-within-category.sql:32-35`). `docs/SECURITY.md`'s SEC-MED-4 frames this risk window as opening only once "T-003 (not yet built)" starts writing slugs — I verified that framing is incomplete: the risk window actually opens at **this ticket's own merge**, through a save path this ticket doesn't touch and isn't asking to fix, but which is now newly capable of this side effect purely because `Product` gained a `slug` field it didn't have before. **Impact today:** none — nothing public-facing reads `.slug` yet. **Impact once this merges:** any category saved from `/admin/business` before T-003 ships acquires a slug that was never validated, never checked for collision at save time, and can never be told apart afterward from a "properly" T-003-assigned one — T-003's write path will have to treat *every* stored slug as already-possibly-untrustworthy from day one, not just legacy pre-T-001 rows. **Recommend:** (1) fold explicitly into T-003's acceptance criteria — T-003 cannot assume "no category has a slug yet" as a precondition; (2) flag to the user as an interim operational note: avoid adding a category whose title duplicates or nearly duplicates an existing one, and avoid reordering categories, on `/admin/business` between now and T-003 shipping, since either can be silently frozen by the very next routine Save.

### Dispatch risk 1 — Revalidation end-to-end

**Is `revalidatePath("/sitemap.xml")` meaningful? No — confirmed, not just suspected, via the actual build output.** `src/lib/supabase/server.ts::createClient()` unconditionally calls `cookies()` from `next/headers`. `sitemap.ts` now calls `getSettings("business")` → `createClient()` → `cookies()`, which forces the entire `sitemap.ts` render into per-request dynamic rendering (Next's documented behavior: a Dynamic API used anywhere in a metadata-route's render path takes it out of static/ISR generation). This pass's own `npm run build` (below) independently confirms it: `/sitemap.xml` builds as **`ƒ` (Dynamic, server-rendered on demand)**, not `○` (Static) — there is no cached output for `revalidatePath` to ever purge; every single request already re-executes `getSettings` fresh. The same is true of `/what-we-do/[category]` itself (also `ƒ`) and of the pre-existing `/what-we-do` (already `ƒ` before this diff). This generalizes beyond just the new sitemap line: **every `revalidatePath('/what-we-do'…)` call in this codebase — the new one and the pre-existing T-003 ones — is currently a no-op**, because there was never a cache entry to invalidate in the first place; freshness comes entirely from forced dynamic rendering, not from revalidation. Functionally harmless (a no-op `revalidatePath` doesn't error, and this is the safe/over-invalidation direction) — but the diff's own code comment ("it was not before T-005, which would have left a stale sitemap between deploys until its own time-based revalidation caught up") overstates what the call achieves: there is no time-based revalidation window here to catch up from, because `export const revalidate = 60` is likewise moot on a `cookies()`-forced-dynamic route. See WARN-1.

**Would a rename or delete leave anything stale? No — but not because of revalidation working; because there's no cache to begin with**, per the above. A renamed category's old URL simply starts 404ing on the very next request (no redirect exists for it — see dispatch item 5 below); a deleted category's URL does the same, and drops out of `/sitemap.xml` on its very next fetch, again because the route always re-fetches, not because a targeted invalidation fired.

### Save-on-blur + Retry — races, interleaving, and row-keying (the dispatch's specific hunt)

**Row keying — confirmed clean, the T-002/WARN-4 pattern does NOT recur here.** `{products.map((product, i) => (<ProductRow key={product.id} ... index={i} .../>))}` (`CategoryProductsManager.tsx:255-267`) — the React `key` is `product.id` (stable, DB-generated UUID); `index={i}` is passed as an ordinary *prop* only (for "Product N of M" display and up/down boundary-disabling), never as the key. Reordering or deleting a row cannot hand its local `draft`/`busy`/`error`/`justSaved` state to a sibling — each product id always maps to the same component instance or a genuine mount/unmount, never a silent reuse. This is a direct, positive contrast with the still-open `ObjectListEditor` index-keying gap (T-002 WARN-4 / **T-010**, not yet fixed) — T-004's new component does not repeat it.

- 🟡 **New finding — a row's Name/Description save and its Image-field save are two independent, unguarded requests to the same row, and an out-of-order response can let the earlier (stale) one silently overwrite the later one's freshly-saved image.** `ProductRow`'s Name and Description `<input>`/`<textarea>` share one `busy` flag and are both `disabled={busy}` (`CategoryProductsManager.tsx:542,558`), which does correctly serialize saves *between those two fields* — confirmed by tracing React's synchronous re-render-before-next-event model, matching `/ui-ux`'s own stated reasoning, which I independently agree with for that pair. **But `<ImageUploadField>` (`:532`) is rendered with no `disabled` prop, and `ImageUploadField`'s own signature (`{label, value, onChange}`, confirmed by re-reading the full file) has no `disabled` parameter to plumb one into even if `ProductRow` tried** — so the image dropzone stays fully interactive while a Name/Description-triggered `persist()` is still in flight for the *same row*. Concrete sequence: (1) admin edits Name, blurs → `persist()` #1 starts, sends `{name: NEW, description: OLD, image: OLD, sort_order}`; (2) *before #1 resolves*, the same admin drags a new photo onto the still-enabled image dropzone → upload completes → `onChange(url)` fires → `persist({image: url})` #2 starts, sends `{name: NEW, description: OLD, image: NEW, sort_order}` (its own `draft` snapshot, correct at the moment it was taken); (3) both calls independently succeed at the DB layer (`updateCategoryProduct` has no version/ETag check — it's an unconditional full-row overwrite keyed only by `id`); (4) **if #1's response arrives after #2's** (plausible: #2 only starts after a full image upload round trip completes, but network/server response timing for #1 is not guaranteed to beat it), #1's `then` branch runs last and calls `setDraft({..., image: result1.product.image})` using **its own stale snapshot's returned row — the OLD image** — silently reverting both the database row and the on-screen preview back to the pre-upload image, with a "Saved" confirmation flashing both times and **no error shown anywhere**, since each individual request genuinely succeeded. The newly-uploaded file itself is not lost (still a valid Storage object at its URL), but the row's `image` field is wrong until someone notices and re-uploads. **Reachable via entirely ordinary UI use, no crafted call needed** — same class of bug as the site's other already-accepted concurrent-write findings (`docs/SECURITY.md` SEC-MED-5, SEC-MED-12) and structurally identical in spirit to T-002's WARN-2 ("whichever resolves last wins, not whichever was picked last"), just occurring *across* a row's two save triggers instead of within one upload field's own re-entrancy. **Not blocking** for the same reason those were graded non-blocking: no auth/security impact, no cross-row/cross-category corruption, recoverable by re-uploading, and — per the realistic timing (image upload is normally much slower to *start* its own row-save than a plain text blur) — the dangerous ordering is the less common case, not the default one. **Fix proposal:** either add a `disabled` prop to `ImageUploadField` (shared component — affects every consumer) and wire `disabled={busy}` from `ProductRow`, or (narrower, local-only) track a monotonic per-row request-sequence ref in `ProductRow` and ignore a `persist()` resolution that isn't from the latest call — the same fix shape already recommended for T-002's WARN-2. - 🟡 **New finding — `AddProductForm` is not remounted on a category switch, so an in-progress, already-uploaded draft (image/name/description) silently survives a category change and can attach to the wrong category.** `<AddProductForm categorySlug={selected.slug} onCreated={handleCreated} />` (`CategoryProductsManager.tsx:242`) carries no `key` prop.
