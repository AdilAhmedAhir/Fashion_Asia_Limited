### Findings

- 🟡 **WARN-1** — `checkImageSizeAdvisory` silently mis-reports `offProportion` for a 0×0 image — `src/lib/upload-limits.ts:98-99` — `ratio = width / height` is `0/0 = NaN` when both are zero; `NaN < 1` and `NaN > 2` are both `false` in JS, so `offProportion` comes back `false` instead of `true`, while `tooSmall` correctly comes back `true`. Net effect: a warning still fires (not a silent-failure bug), but it always claims "smaller than the recommended…" and never "a noticeably different shape," which is a strange thing to say about a 0×0 image. Trigger condition is narrow: `img.onload` firing with `naturalWidth === naturalHeight === 0` for a genuinely-decoded JPEG/WebP is close to unreachable (both formats always encode non-zero dimensions in their header on a successful decode; an actual decode failure fires `onerror`, not `onload`, and is already handled at `ImageUploadField.tsx:108-111`). The realistic path in, if any, is a mislabeled non-raster file (e.g. a sizeless SVG renamed to `.jpg`) that some browser decides to decode anyway — client-side format sniffing hasn't run yet at this point (`sniffImageFormat` is server-side only, later). No crash, no hard-block bypass, no data corruption — purely a cosmetic mis-statement inside a non-blocking advisory string. **Fix proposal:** guard the division, e.g. `const ratio = height === 0 ? Infinity : width / height;`, or short-circuit to `{ tooSmall: true, offProportion: true }` whenever `width <= 0 || height <= 0`.

- 🟡 **WARN-2** — Rapid successive file picks race; whichever upload's network round-trip resolves *last* wins, not whichever was picked last — `src/components/admin/ImageUploadField.tsx:97-139`. `handleFile` is re-entrant with no guard: the file `<input>` (`:209-219`) and the drop zone are never `disabled`/inert while `busy` is `true`, and there is no request-sequence token, no `AbortController`, no "ignore a stale resolution" check. If a staff member picks file A, then — before A's `readDimensions` + `uploadOptimizedImage` round trip finishes — picks file B, both invocations run concurrently. Each clears `error`/`warning` via its own `setError(null)`/`setWarning(null)` at entry (so no simultaneous stale display), but the *last* promise to resolve calls `onChange(result.url)` + `setWarning(advisory)` last, overwriting whatever the other call already wrote — even if that means the field ends up showing file A's image/warning when the user's actual last action was picking file B. **Pre-dates T-002** (the old `tooBig` was awaited the same unguarded way) — T-002 doesn't introduce the race, but it does add a second piece of state (`warning`) that now rides the same unguarded race the image `value` already had. Impact is a confusing-but-recoverable admin-UI moment (re-picking fixes it; both files still separately land in storage — only the client's *displayed* final state can pick the "wrong" one), not a security or data-integrity issue. **Fix proposal:** disable the input/dropzone while `busy`, and/or track a monotonic "latest pick" ref and ignore a resolution that isn't from the latest call. Recommend a `/pm` follow-up rather than reopening T-002 for pre-existing behavior it didn't originate.

- 🟡 **WARN-3** — Manually editing the raw path `<input>` (`ImageUploadField.tsx:248-255`) doesn't clear a stale `warning`/`error` left over from a previous upload attempt on the same field instance — the reset at `:98-99` only runs inside `handleFile`, which the path `<input>`'s own `onChange={e => onChange(e.target.value)}` never calls. Repro: upload a small photo (warning appears: "smaller than the recommended…"), then use the same field's editable path box — kept editable on purpose, "the built-in photographs are repo paths, not uploads" (`:247`) — to switch to a different, already-correctly-sized built-in image path. The thumbnail and stored `value` correctly update, but the old warning stays on screen describing an image that is no longer selected. The same gap already existed for `error` before T-002; this diff adds a second instance of it. Cosmetic/misleading, not a data bug — the saved `value` itself is always correct. **Fix proposal:** also clear `error`/`warning` inside the path `<input>`'s `onChange` handler.

- 🟡 **WARN-4** — Reordering or deleting a product/facility-photo row can hand one item's leftover warning/error to a *different* item's upload field — root cause is **outside T-002's diff**, in `src/components/admin/SettingsForm.tsx:167` (`{items.map((item, i) => (<div key={i} …>`) and `:192-193` (`<ImageUploadField key={f.key} … value={item[f.key] …} />`). The outer per-row key is the array index `i`, not a stable per-item id, so React reconciles a reordered/shortened list by re-rendering the *same* `ImageUploadField` instances at each index with new `value` props rather than mounting fresh ones — the field's own local `error`/`warning`/`busy` state (only ever reset inside `handleFile`, see WARN-3) survives the reorder attached to whatever now occupies that slot. Concretely: product #1 gets a "smaller than recommended" warning; staff clicks "move down" on product #2 (swapping #1 and #2); product #2's image field — now at array index 0 — inherits and displays product #1's stale warning, describing product #1's dimensions, not its own. Same mechanism on delete for every row after the deleted one. Reachable today from `/admin/business`'s "Product Cards" `ObjectListEditor` (move-up/move-down/remove buttons render unconditionally) and from `/admin/homepage`'s facility-photo list. **Not a T-002 regression** — `SettingsForm.tsx` isn't in this ticket's file list and this diff doesn't touch it — but T-002 makes the *consequence* more visible, since "too small"/"off-proportion" warnings will fire far more often in practice than the rare hard-block error the same gap already affected. Consistent with `docs/ROADMAP.md` T-001's own acceptance criteria, which already flags that `site_settings.business.products` items have no stable id yet (`src/lib/site-content.ts:318-322` — `Product` is `{ title, description, image }`, no `id`) — a real per-item key isn't available until T-001 lands. **Fix proposal:** once T-001 provides a stable id, key `ObjectListEditor`'s rows by that id instead of index; until then, at minimum have `ImageUploadField` reset `error`/`warning` whenever its `value` prop changes for a reason other than its own `handleFile` call. Recommend a `/pm` follow-up ticket; does not block T-002.

- 🟢 **INFO-1** — Wording nit at extreme aspect ratios — `src/lib/upload-limits.ts:97` — `tooSmall` is `width < 1200 || height < 900`, an OR across two independent dimensions, so a very wide/short image that still clears the 2400px hard cap (e.g. 2400×100) is labeled "smaller than the recommended 1200×900px" even though its width is exactly 2× the recommendation — only its height is short. The shown numbers (`This image is 2400×100px…`) are still accurate, so nothing is factually wrong, just slightly imprecise about which dimension is the actual problem. Not worth blocking on.

No unit-test or E2E runner is installed (`docs/TECH_STACK.md` → "Testing framework: None installed"; `docs/WORKFLOW.md` §4: "`/qa static` = code review against the ticket's diff — there is no test suite to run").
