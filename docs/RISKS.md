# RISKS.md — The Most Likely Ways This Design Fails

> GENESIS Phase 2, 2026-09-28. Plain language: what could fail, how we'd notice, how bad it
> is, and what stops it. The Phase 3 team is justified against these entries.

| # | What could fail | How we'd notice | Severity | Mitigation |
|---|---|---|---|---|
| **R1** | **Anyone who gets a Supabase account becomes a full admin.** There's no admin role: every signed-in account can edit the site, publish products, and read contact, career and grievance submissions (personal data). Today the "Allow new users to sign up" toggle is the only guard, and it was still **on** on 2026-09-28. | Unknown users in Supabase Auth → Users; content or products nobody at FAL added. | 🔴 High | **Now:** the owner turns sign-ups OFF and removes unknown users. **Next:** an explicit admin allowlist, checked in the middleware, every writing action and RLS. It needs `/debate` and `/security-review` (SEC-HIGH-2). |
| **R2** | **Schema and access rules drift away from the repo.** Tables and policies are hand-applied in the dashboard. `supabase-schema.sql` is missing the live `authenticated` policies and the storage bucket rules. A rebuild from the repo would break the admin or open data. | A replay or disaster recovery fails; a new table ships without RLS. | 🔴 High | Every change goes through `db/migrations` with STATUS headers, and the owner applies it. Periodically copy the live policies back into `supabase-schema.sql` (WORKFLOW §7 #2). |
| **R3** | **Testing writes into production data.** Local dev and production share one database, so an agent or a person "testing" a form or an admin save changes the live site. | Test rows on the live site; stray submissions. | 🟠 Medium-high | Law: read-only QA only (WORKFLOW §4). Admin writes come from owner checklists that use clearly named test rows and end with a cleanup step. |
| **R4** | **Admin actions fail silently or look like they worked.** Thrown Server Action errors are redacted in production. | Staff report "I saved, but nothing changed". | 🟠 Medium | The `{ ok, error }` contract. Settings were fixed in T-012; reports, jobs and leaders in T-015 (**merged, not yet deployed**). Media is still open (T-019). |
| **R5** | **A release reaches one repo but not the other, or goes out under the wrong name, or leaks the GitHub token.** | `origin` and `client` show different `main` SHAs; commits carry other names; the plaintext token in `.git/config` is misused (SEC-MED-14). | 🟠 Medium | `/ship` pushes both and verifies both SHAs. `.githooks/` enforce commit names. The owner rotates the token into a fine-grained, Keychain-stored one. |
| **R6** | **The catalog stays empty and the 90-day number is missed.** Every category shows "Coming Soon". The one-time bootstrap Save hasn't been run, so the editor is locked; a category renamed before that Save changes its URL. | `public.products` count per category (the 90-day metric). | 🟡 Medium | The owner runs the bootstrap Save and the T-004 checklist. The T-016 editor fixes land before staff use it at scale. Send CLIENT_QUESTIONS Q02 and Q03 to FAL. |
